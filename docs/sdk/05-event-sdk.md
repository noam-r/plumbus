# Plumbus Event SDK Specification

## Purpose

This document defines the **Event SDK**, the programming interface used
to declare and work with domain events in Plumbus applications.

Events represent **facts that occurred in the system**. They are emitted
by capabilities or flows and consumed by:

-   other flows
-   event-handler capabilities
-   integrations
-   analytics systems

The Event SDK defines:

-   the `defineEvent()` primitive
-   event schemas
-   event versioning
-   event emission rules
-   event handling capabilities
-   event replay
-   governance and audit visibility

The Event SDK enables reliable **event‑driven architecture** while
preserving traceability and system explainability.

------------------------------------------------------------------------

## Conceptual Model

An **event** represents a completed domain action.

Examples:

-   `customer.created`
-   `invoice.generated`
-   `refund.approved`
-   `ticket.classified`

Events should represent **past tense domain facts** rather than
commands.

Good examples:

-   `refund.approved`
-   `invoice.sent`

Bad examples:

-   `approveRefund`
-   `sendInvoice`

Commands belong to capabilities, not events.

------------------------------------------------------------------------

## Event File Structure

Events should be defined in dedicated files.

Example:

    app/events/refund-approved.event.ts
    app/events/customer-created.event.ts

Keeping events explicit improves:

-   discoverability
-   schema validation
-   governance analysis
-   AI-assisted navigation

------------------------------------------------------------------------

## defineEvent()

Events are declared using:

``` ts
defineEvent(...)
```

Example:

``` ts
export const RefundApproved = defineEvent({
  name: "refund.approved",

  payload: z.object({
    refundId: z.string(),
    approvedBy: z.string(),
  })
})
```

This declaration defines the **event contract** used for validation and
documentation.

------------------------------------------------------------------------

## Event Contract Fields

## Identity

Each event must define:

-   `name`

Optional metadata:

-   description
-   domain
-   version
-   tags

Example:

``` ts
name: "refund.approved"
```

------------------------------------------------------------------------

## Payload Schema

The `payload` field defines the event data structure.

Example:

``` ts
payload: z.object({
  refundId: z.string(),
  approvedBy: z.string(),
})
```

Payload schemas are used for:

-   validation
-   generated documentation
-   AI briefs
-   replay safety

Events without payloads should still declare an empty schema.

------------------------------------------------------------------------

## Event Versioning

Events may evolve over time.

Versioning strategies may include:

-   explicit version field
-   version suffix in name

Example:

    refund.approved.v1
    refund.approved.v2

Consumers should declare which versions they support.

Versioning prevents breaking downstream consumers.

------------------------------------------------------------------------

## Event Emission

Events are emitted through the runtime context.

Example:

``` ts
await ctx.events.emit("refund.approved", {
  refundId: refund.id
})
```

The framework ensures that emitted events:

-   match their payload schema
-   are recorded in the outbox
-   generate audit records
-   trigger subscribed flows

Capabilities should never publish directly to messaging infrastructure.

------------------------------------------------------------------------

## Event Delivery Model

Plumbus uses an **outbox pattern** for reliable event delivery.

Event lifecycle:

1.  capability emits event
2.  event stored in outbox table
3.  event dispatcher reads outbox
4.  dispatcher publishes delivery jobs
5.  consumers process events

This ensures:

-   no lost events
-   transactional consistency
-   safe retries

------------------------------------------------------------------------

## Event Handlers

Events may trigger event-handler capabilities.

Example:

``` ts
export const onRefundApproved = defineCapability({
  name: "onRefundApproved",
  kind: "eventHandler",

  trigger: {
    event: "refund.approved"
  },

  handler: async (ctx, payload) => {
    await ctx.flows.start("sendRefundConfirmation", payload)
  }
})
```

Event handlers allow domain reactions without tightly coupling
components.

------------------------------------------------------------------------

## Event Metadata

Events should include metadata automatically generated by the framework.

Metadata may include:

-   eventId
-   timestamp
-   actor identity
-   tenantId
-   correlationId
-   originating capability

This metadata improves traceability.

------------------------------------------------------------------------

## Event Replay

The system should support event replay.

Replay allows:

-   rebuilding projections
-   debugging workflows
-   reprocessing failed consumers

Replay tools should respect:

-   version compatibility
-   idempotency requirements

------------------------------------------------------------------------

## Idempotency

Event consumers must be idempotent.

If the same event is delivered multiple times, the system should remain
consistent.

This is especially important for:

-   retries
-   replay
-   distributed processing

------------------------------------------------------------------------

## Governance Visibility

Events provide signals for governance analysis.

The governance system may detect:

-   sensitive data in event payloads
-   missing event schemas
-   excessive event emission

These signals help detect risky architectural patterns.

------------------------------------------------------------------------

## Audit Integration

Event emission automatically records audit signals.

Audit records may include:

-   event name
-   payload metadata
-   actor identity
-   timestamp

Sensitive fields should be masked according to classification metadata.

------------------------------------------------------------------------

## AI-Friendly Event Design

Events should remain easy for AI agents to understand.

Guidelines:

-   use descriptive event names
-   keep payload schemas small
-   avoid deeply nested payloads
-   document event meaning clearly

Clear event definitions improve automated reasoning.

------------------------------------------------------------------------

## Best Practices

Recommended practices:

-   use past‑tense event names
-   keep payloads minimal
-   version events when schema changes
-   design consumers to be idempotent
-   emit events only for meaningful domain changes

Events should represent **facts**, not internal implementation details.

------------------------------------------------------------------------

## Summary

The Event SDK defines how Plumbus applications represent and communicate
domain events.

By combining explicit event schemas, reliable delivery through the
outbox pattern, and integration with capabilities and flows, the
framework enables systems that are:

-   loosely coupled
-   reliable
-   auditable
-   explainable
-   safe for AI‑assisted development
